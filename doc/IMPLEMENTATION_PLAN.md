# План реализации TabletDisplayWindows

> Статус 2026-08-14: сквозным тестом подтверждены 1280×800 и портретный 800×1280 @60. D3D11 VideoProcessor выполняет BGRA→NV12 и поворот на GPU, NV12-текстура без CPU-копии поступает в Quick Sync; CPU fallback сохранён. Исправлена утечка output samples; 60-секундный soak держит ~96 МБ private memory. Следующий шаг — длительный reconnect/soak-тест, затем shared texture driver→Host.

## 1. Цель и границы MVP

Сделать Windows-приложение и Indirect Display Driver, которые добавляют в Windows 11 один настоящий расширяемый дисплей и передают его изображение на Android-планшет по USB через ADB.

MVP должен обеспечивать:

- Windows 11 x64;
- один виртуальный монитор;
- режимы 1280×800/1920×1200 и портретные 800×1280/1200×1920 при 30 и 60 Гц;
- H.264/AVC с аппаратным кодированием, когда оно доступно;
- передачу по одному двунаправленному TCP-соединению через `adb forward`;
- автоматическое восстановление после отключения кабеля или перезапуска Android-приложения;
- преобразование одиночного touch в мышь на виртуальном дисплее;
- диагностические логи без содержимого пользовательского экрана.

В MVP не входят: собственный WinUSB-протокол, Wi-Fi, HEVC, DRM-контент, звук, несколько планшетов, полноценный multitouch, публично подписанный установщик драйвера.

## 2. Целевая архитектура

```text
Windows Desktop
      ↓
TabletDisplayDriver.dll (UMDF 2 + IddCx)
      ↓ D3D11 swap-chain frames
Driver/Host IPC
      ↓
TabletDisplayHost.exe
  ├─ Media Foundation H.264 encoder
  ├─ protocol/session controller
  ├─ ADB forward + TCP transport
  └─ touch-to-Windows input
      ↓ USB / ADB
TabletDisplayAndroid
```

Процессы разделены намеренно: драйвер отвечает только за жизненный цикл виртуального дисплея и выдачу кадров, host — за внешние процессы, сеть, кодек, повторные подключения и ввод.

Реализованная совместимая схема IPC:

- device interface с read-only IOCTL;
- один защищённый latest-frame BGRA buffer: новый кадр заменяет старый и драйвер не ждёт Host;
- D3D11 staging texture для совместимости с любым render adapter;
- после доказательства работоспособности — D3D11 shared texture/fence для минимизации копирований;
- отсутствие потребителя не должно блокировать callback или swap-chain processing драйвера.

Device interface доступен обычному пользователю только на чтение. Zero-copy D3D11 shared texture остаётся оптимизацией после сквозной проверки совместимого пути.

## 4. Этапы реализации

### Этап 0. Инструменты и воспроизводимая сборка

1. Проверить установленные MSVC Build Tools, Windows SDK, WDK/EWDK, CMake при необходимости и `adb`.
2. Зафиксировать конкретные поддерживаемые версии SDK/WDK и целевую версию Windows в `doc/BUILD.md`.
3. Создать solution и два проекта: UMDF/IddCx driver и обычное x64 host-приложение.
4. Настроить Debug/Release x64, предупреждения компилятора, `/permissive-`, C++20 и статический анализ.
5. Добавить VS Code tasks для сборки драйвера, host, тестов, установки и удаления test-signed драйвера.
6. Добавить скрипты, которые проверяют окружение и завершаются с понятной ошибкой, не меняя глобальный `PATH`.

Критерий готовности: чистый checkout собирается одной документированной командой; host запускается, а тестовый пакет драйвера создаётся в предсказуемом каталоге.

### Этап 1. Спецификация протокола и тестовый транспорт

1. Создать `doc/PROTOCOL.md` с порядком байтов, размерами полей, ограничениями длины и правилами совместимости.
2. Определить общий заголовок сообщения: magic, версия, тип, flags, payload length, sequence и timestamp.
3. Зафиксировать сообщения MVP: `HELLO`, `HELLO_ACK`, `DISPLAY_INFO`, `VIDEO_CONFIG`, `VIDEO_FRAME`, `REQUEST_KEYFRAME`, `TOUCH`, `PING`, `PONG`, `ERROR`.
4. Выбрать H.264 Annex B как начальный формат elementary stream; явно описать SPS/PPS, IDR и границы access unit.
5. Реализовать безопасный incremental parser: лимиты payload, обработка частичных чтений, неизвестных типов и несовместимой версии.
6. Написать unit-тесты сериализации и golden vectors, пригодные для копирования в Android-тесты.
7. Реализовать тестовый host, отправляющий синтетические кадры/пакеты без драйвера.

Критерий готовности: Windows parser проходит positive/negative tests, а Android-проект может проверить те же бинарные векторы.

### Этап 2. Минимальный виртуальный дисплей IddCx

1. Взять за основу актуальные официальные паттерны IddCx/Indirect Display Driver, не копируя ненужные sample-компоненты.
2. Реализовать инициализацию WDF/IddCx, adapter и monitor arrival/departure.
3. Создать стабильный идентификатор монитора и минимальный EDID/описание режимов.
4. Объявить только режимы MVP и корректно валидировать выбранный Windows режим.
5. Реализовать назначение и отмену swap chain, поток обработки кадров и корректное завершение.
6. Добавить DeviceGroupId и настройки изоляции UMDF в INF.
7. Не запускать ADB, сеть или кодек из драйвера.

Критерий готовности: после test-sign/install Windows показывает второй монитор, разрешает «Расширить эти дисплеи», смену всех заявленных режимов, sleep/wake и повторную установку без зависания.

### Этап 3. Прототип Driver/Host IPC

1. Создать отдельный spike, передающий из swap chain номер кадра, размеры, формат и тестовые пиксели в host.
2. Проверить доступные форматы IddCx swap chain и необходимые D3D11 преобразования.
3. Измерить варианты:
   - GPU → staging texture → shared memory;
   - D3D11 shared resource между процессами;
   - другой поддерживаемый механизм, если ограничения UMDF блокируют shared handles.
4. Реализовать bounded queue на 2–3 кадра; при перегрузке отбрасывать старые, а не накапливать задержку.
5. Обработать запуск host позже драйвера, падение host и его повторное подключение.
6. Документировать выбранный IPC, модель владения, синхронизацию и security descriptor.

Критерий готовности: host непрерывно получает проверяемые кадры не менее 30 минут, перезапускается независимо, а driver не блокируется при отсутствии host.

### Этап 4. ADB и управление соединением

1. Находить `adb` предсказуемо: настройка проекта → известный Android SDK → `PATH`; логировать выбранный путь.
2. Выполнять `adb devices -l` и различать `device`, `offline` и `unauthorized`.
3. Для ровно одного готового устройства выполнить `adb -s <serial> forward tcp:27183 tcp:27183`.
4. Подключаться к `127.0.0.1:27183`, выполнять handshake и проверять версию/возможности Android.
5. Реализовать timeout, heartbeat, отмену операций и exponential backoff с верхней границей.
6. При нескольких устройствах требовать явный serial из конфигурации, не выбирать случайно.
7. Корректно удалять только созданный приложением forward при завершении.

Критерий готовности: подключение устанавливается после запуска Android-приложения и автоматически восстанавливается после отключения/подключения USB без перезапуска Windows.

### Этап 5. H.264 encoder

1. Перечислить Media Foundation H.264 MFT и выбрать аппаратный encoder с поддержкой D3D11; иметь явный software fallback только для диагностики.
2. Создать D3D11 device с video support и согласовать adapter, на котором находятся входные текстуры.
3. [Готово] Преобразовать входной BGRA в NV12 на D3D11 VideoProcessor; совместить с поворотом и передать ту же NV12-текстуру аппаратному MFT без CPU-копии. Оставить CPU fallback.
4. Настроить low-latency режим, отсутствие B-frames, GOP около 1–2 секунд, bitrate и частоту кадров из согласованной конфигурации.
5. Нормализовать выход encoder в формат, зафиксированный протоколом; отправлять SPS/PPS до первого IDR и после изменения конфигурации.
6. Реализовать принудительный keyframe по запросу Android и после потери/восстановления соединения.
7. Не держать swap-chain frame во время сетевой отправки; все медленные операции вынести из критического пути драйвера.

Начальные профили качества:

| Режим | FPS | Стартовый bitrate |
|---|---:|---:|
| 1280×800 | 30 | 5 Mbit/s |
| 1280×800 | 60 | 8 Mbit/s |
| 1920×1200 | 30 | 8 Mbit/s |
| 1920×1200 | 60 | 12 Mbit/s |
| 800×1280 | 60 | 8 Mbit/s |
| 1200×1920 | 60 | 12 Mbit/s |

Значения являются начальными и уточняются измерениями текста, видео и движения рабочего стола.

Критерий готовности: Android аппаратно декодирует поток; после статической картинки, быстрого движения и смены режима нет постоянных артефактов или неограниченного роста задержки.

### Этап 6. Сквозной video pipeline

1. Связать кадры IPC, encoder и transport через bounded queues и общий cancellation token.
2. Передавать монотонные frame number и capture timestamp для измерения задержки.
3. Отбрасывать устаревшие неключевые кадры при backpressure.
4. При reconnect начинать новую video session с `VIDEO_CONFIG` и IDR.
5. Обрабатывать смену разрешения/частоты как транзакцию: остановить encoder, очистить очереди, пересоздать ресурсы, отправить новую конфигурацию и IDR.
6. Добавить счётчики capture/encode/send FPS, dropped frames, queue depth, bitrate и reconnect count.

Критерий готовности: 60-минутный прогон без роста памяти; после reconnect и смены режима изображение восстанавливается автоматически.

### Этап 7. Ввод с планшета

1. Принимать нормализованные координаты, action, pointer id и timestamp только после успешного handshake.
2. Сопоставлять координаты с актуальным прямоугольником именно виртуального монитора, включая отрицательные координаты рабочего стола.
3. Для MVP преобразовать один палец в move/down/up мыши через поддерживаемый Windows API ввода.
4. Гарантировать принудительный `UP` при разрыве соединения, чтобы не оставлять зажатую кнопку.
5. Игнорировать невалидные координаты, неизвестный pointer и чрезмерную частоту событий; не выполнять произвольные команды из сети.
6. Оставить multitouch/pen/keyboard отдельным этапом после MVP.

Критерий готовности: касание точно управляет окнами на виртуальном дисплее при любом расположении мониторов и не оставляет зажатых кнопок после отключения.

### Этап 8. Надёжность, безопасность и диагностика

1. Ввести единый structured logging с component, level, event id и session id.
2. Ограничить TCP только loopback; не открывать порт в LAN и не изменять Windows Firewall.
3. Проверять все размеры, integer overflow и lifetime входных буферов до выделения памяти.
4. Сделать graceful shutdown для console/service режима host.
5. Собрать crash dumps и диагностический bundle без кадров экрана и персональных данных.
6. Проверить Driver Verifier только с настройками, подходящими UMDF/IddCx, и сохранить процедуру восстановления.
7. Прогнать static analysis и sanitization/fuzzing protocol parser там, где это доступно.

Критерий готовности: malformed input не приводит к crash или большим allocations; логи позволяют определить стадию сбоя без доступа к экранному содержимому.

### Этап 9. Установка и эксплуатация

1. Создать скрипты test-sign/install/update/uninstall с явными проверками прав администратора и точного INF-пути.
2. Описать включение test signing только для разработки и способ безопасного возврата обычной конфигурации.
3. Упаковать host-конфигурацию, логи и запуск в понятные каталоги; не требовать запуска VS Code.
4. Для личного MVP допустим ручной запуск host; Windows service/tray UI вынести в отдельную задачу после стабилизации pipeline.
5. Публичное распространение не начинать до выбора схемы подписи драйвера и проверки требований Microsoft на актуальную дату.

Критерий готовности: на чистой тестовой Windows-машине по инструкции устанавливается driver, запускается host и полностью удаляется без оставшихся устройств/forward rules.

## 5. Тестовая стратегия

### Автоматические тесты

- protocol serialization/parsing, partial reads, invalid lengths, version mismatch;
- ring/bounded queue и политика drop;
- display-to-normalized coordinate mapping;
- reconnect state machine и таймеры;
- encoder configuration и Annex B parsing;
- golden binary vectors, одинаковые для Windows и Android.

### Интеграционные тесты

- synthetic producer → encoder → recorded stream → Android decoder;
- driver → IPC → host без Android;
- host → ADB → Android без driver с тестовым видео;
- полный pipeline с reconnect на каждой границе.

### Матрица ручной проверки

- Intel, AMD и NVIDIA GPU, доступные для тестирования;
- USB 2.0 и USB 3.x;
- 1280×800/1920×1200 и 800×1280/1200×1920, 30/60 Гц;
- различное расположение виртуального монитора слева/справа/выше основного;
- lock/unlock, sleep/wake, display mode change;
- cable unplug, Android force-stop, `adb kill-server`, host restart;
- статический текст, прокрутка, видео и быстрое перемещение окон.

## 6. Метрики MVP

- время до первого изображения после готового ADB: целевое значение ≤ 3 секунд;
- end-to-end latency: измерить; первоначальная цель ≤ 100 мс на поддерживаемом оборудовании;
- отсутствие неограниченного роста latency при перегрузке;
- reconnect после возврата устройства: целевое значение ≤ 10 секунд;
- 60 минут работы без crash и заметного роста private working set;
- поток 1920×1200@60 укладывается в практическую пропускную способность USB 2.0 при выбранном bitrate.

## 7. Зависимости и порядок совместной разработки

1. Сначала согласовать `PROTOCOL.md` и golden vectors в обоих проектах.
2. Параллельно сделать Android test receiver и Windows synthetic sender.
3. Независимо поднять IddCx display и проверить Driver/Host IPC.
4. Подключить Media Foundation encoder к test frames, затем к реальным frames.
5. После стабильного видео добавить touch.
6. Изменения wire format считаются завершёнными только после обновления обоих проектов и cross-version теста.

## 8. Условия завершения MVP

MVP завершён, когда пользователь подключает разрешённый Android-планшет по USB, запускает Android-приложение и Windows host, видит новый монитор в настройках Windows, выбирает расширение рабочего стола, получает стабильное полноэкранное изображение на планшете и управляет этим дисплеем одним пальцем. Отключение и повторное подключение кабеля восстанавливает сеанс без переустановки драйвера.
